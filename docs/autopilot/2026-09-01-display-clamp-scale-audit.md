# Display เลขคิวสเกลใหญ่ตามจอด้วย clamp — audit

รอบ `auto/Booth_Management_6_7/2026-09-01_0006` · เกณฑ์ข้อแรกของกลุ่ม `ui-overhaul` ที่ถูกปิด

สเปก: `docs/superpowers/specs/2026-08-03-ui-overhaul-design.md` บรรทัด 50 —
*จอใหญ่/TV (Display): เลขคิวสเกลด้วย `clamp()` ให้ใหญ่ตามจอ (เช่น `clamp(96px, 22vw, 320px)`) เห็นสุดห้อง*

**ไม่ได้แก้ `src/` แม้แต่บรรทัดเดียว** โค้ด production ถูกต้องอยู่แล้ว และตรงกับตัวอย่างในสเปกเป๊ะ
สิ่งที่ขาดคือเทสต์ — และช่องว่างที่ขาดไม่ใช่ "ไม่มีใครเช็ค clamp" แต่เป็น **เช็คผิดชั้น**

## ช่องว่างที่เจอ: clamp ที่ "ประกาศไว้" ≠ clamp ที่ "ทำงาน"

ก่อนรอบนี้มีเทสต์สามตัวแตะเกณฑ์นี้อยู่แล้ว ทั้งสามอ่าน **ค่าที่ประกาศ**:

| เทสต์ | สิ่งที่พิสูจน์ |
|---|---|
| `displayCentering.audit` **B1** | เลขคิวทั้งสองตัวประกาศ `clamp()` · `vw > 0` · `min ≥ 48` · `max > min` |
| `displayGlanceable.audit` **Z1** | เลข serving ชนะ callout เตรียมตัว ครบทั้งสามพารามิเตอร์ |
| `displayGlanceable.audit` **Z2** | `min` ของ serving ชนะหัวข้อ fixed ที่ใหญ่ที่สุดบนจอ |

`vw > 0` ดูเหมือนรัดกุม แต่มันหลวมกว่าที่คิดมาก — **`clamp(96px, 1vw, 320px)` ผ่าน B1 ทุกข้อ**
(vw = 1 > 0 ✓, min = 96 ≥ 48 ✓, max > min ✓) และ **ไม่สเกลตามจอเลยสักจอ**: พจน์ 1vw
จะแซะพื้น 96px ได้ก็ต่อเมื่อจอกว้างเกิน **9600px** เลขคิวจะค้างที่ 96px เท่ากันหมด
ทั้งบนมือถือ บน iPad และบนทีวีในหอประชุม โดยที่เทสต์ทุกตัวยังเขียว

ไฟล์ใหม่ `src/displayClampScale.audit.test.tsx` จึงไม่ถามว่า *ประกาศอะไรไว้*
แต่ถามว่า **ค่าที่ประกาศนั้นคำนวณออกมาได้เท่าไร** — ถอดนิยาม CSS ของ `clamp()` กับ `vw`
มาเป็นเลขคณิต แล้วประเมินที่ความกว้างจริงตามที่สเปกระบุ (มือถือ · iPad ตั้ง/นอน · แล็ปท็อป · TV)

"ใหญ่ตามจอ" จึงกลายเป็นสี่ข้อเท็จจริงที่ตรวจได้:

| id | คำกล่าว |
|---|---|
| **W1** | ที่ 390px (มือถือ) เลขทั้งสองอยู่ที่ **พื้น** ของตัวเอง และพื้นนั้น ≥ 48px |
| **W2** | ที่ 1920px (ทีวี) เลขทั้งสอง **โตจนชนเพดาน** — ข้อที่ `vw > 0` พูดไม่ได้ |
| **W3** | หมุน iPad 768 → 1024 แล้วเลข **โตขึ้นจริง** (โตต่อเนื่อง ไม่ใช่กระโดดที่ `md:`) |
| **W4** | ขนาดบนทีวี **≥ 2 เท่า** ของขนาดบนมือถือ — ส่วน "เห็นสุดห้อง" |

และสองข้อที่ปักขอบเขตของ clamp ไว้ (`QueueNumber` เป็น component ที่ใช้ร่วมกับหน้าคนคุมซุ้ม):

| id | คำกล่าว |
|---|---|
| **Q1** | variant `display` clamp · variant `card` **ไม่** clamp · และ **ค่า default คือ card** |
| **Q2** | สวีปซอร์ส: มีแต่ `DisplayScreen.tsx:83` ที่ขอ `size="display"` — อีกสองที่ขอ `card` |

`Q1` เรื่อง default ไม่ใช่เรื่องเล็ก: ถ้า default พลิกเป็น `display` การ์ดคิวบน iPad
ของคนคุมซุ้มจะกลายเป็นเลข 22vw ใบเดียวเต็มจอ โดยที่ไม่มีใครแก้ call site ไหนเลย

## ขอบเขตของหลักฐาน — อะไรที่ *ไม่* ได้พิสูจน์

🚨 **ไม่มีพิกเซลไหนถูกวัด และไม่มีการตั้ง viewport ที่ไหนเลยในไฟล์นี้**
jsdom ไม่โหลด stylesheet ไม่ resolve คลาส Tailwind ไม่คำนวณ layout —
`getBoundingClientRect()` คืนศูนย์ทั้งหมด ไม่มีอะไรถูกเรนเดอร์ที่ 1920px จริงๆ

`sizeAt()` คือ **เลขคณิตบนสตริงที่ประกาศไว้ ไม่ใช่การวัด** ก้าวจาก "ค่านี้คำนวณได้ 320 ที่ 1920"
ไปเป็น "เลขคิวสูง 320px บนทีวีในหอประชุม" อาศัยสองสมมติฐานที่ **สมมติ ไม่ได้พิสูจน์**:

1. Tailwind ปล่อย `text-[clamp(a,b,c)]` ออกมาเป็น `font-size` ตามที่เอกสารบอก
   (arbitrary value ถูกส่งผ่านตรงๆ แต่ **ไม่มีเทสต์ตัวไหนอ่าน CSS ที่ generate ออกมาจริง**)
2. `vw` คือ 1% ของ layout viewport และ `clamp()` คือ min/max ตามสเปก CSS

พูดตรงๆ ว่าไฟล์นี้คืออะไร: **รั้วกันการถดถอย** ที่จับได้สี่แบบ — clamp ถูก *ถอดทิ้ง* ·
ถูก *ทำให้แบนด้วย vw ที่เล็กจนไม่มีผล* · ถูกให้ *เพดานที่ไม่มีจอไหนไปถึง* ·
หรือถูก *สลับเป็นขนาด card แบบ fixed* มันไม่ใช่หลักฐานว่าอะไรมีหน้าตายังไงในหอประชุม

🚨 **ไม่ได้พิสูจน์ว่าตัวเลขบนจอไม่ล้นขอบ** — 22vw × เลขสองหลักที่ 1920px ยังพอดี
แต่ไฟล์นี้ไม่รู้เรื่องความยาวของสตริง `A12` เทียบกับ `A1` เลย เพราะไม่มี layout ให้ดู
(`displayCentering` B3 คุมเรื่อง wrap ไว้คนละมุมหนึ่ง)

🚨 **`Q2` สวีปแค่ `src/screens/*.tsx`** — ถ้ามีคนเรียก `QueueNumber size="display"` จากที่อื่น
(เช่น component ใหม่ใน `src/ui/`) สวีปนี้มองไม่เห็น ตอนนี้ไม่มี call site แบบนั้น

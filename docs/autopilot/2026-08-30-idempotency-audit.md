# Idempotency — audit, fix, and the gap that stays open

รอบ `auto/Booth_Management_6_7/2026-08-30_0004` · เกณฑ์ข้อที่ 5 จาก
`docs/superpowers/specs/2026-08-04-queue-pro-upgrade-design.md`

> Idempotency: กดซ้ำ/สองเครื่องพร้อมกัน ไม่ดึงซ้อน/ข้ามผิด (guard คืน no-op)

ข้อนี้ **ต่างจากสี่ข้อก่อนหน้า**: สี่ข้อนั้นโค้ด production ถูกอยู่แล้ว ขาดแค่เทสต์
ข้อนี้มี **บั๊กจริง** และรอบนี้แก้โค้ด production จริง

---

## 1. บั๊ก — guard เป็น snapshot-state ไม่ใช่ write-once

`queueActions.ts` เป็น pure functions ทุกตัวมี guard ตามที่ spec §3 สั่ง:

```ts
export function callSpecific(order: Order, now: number) {
  if (order.status !== 'waiting') return null
  return { status: 'serving', servingAt: now, announcedAt: now }
}
```

แต่ guard นั้นตรวจ `order` **ตัวที่ถูกส่งเข้ามา** และ `QueuePanel` ส่ง order ที่มาจาก
render closure ซึ่ง **เปลี่ยนเฉพาะตอนมี Firestore snapshot เข้ามา** กดสองครั้งใน render
generation เดียวกัน คลิกที่สองจึงยังเห็น `status` เก่า → guard ผ่านอีกรอบ → เขียนสองครั้ง

pure function ที่รับ order มาตัวเดียวไม่มีความจำ **มันปฏิเสธการกดซ้ำที่มันไม่รู้ว่าเคยเกิดไม่ได้**
ครึ่งที่ขาด (write-once) จึงต้องอยู่ที่ panel ไม่ใช่ที่ action — A1 ปักหมุดข้อนี้ไว้

### วัดจริงรอบนี้ ครบทั้ง 5 ปุ่ม (ไม่ได้เดา)

แผนรอบก่อนบอกว่า "น่าจะใช่ทั้งหมด" — รอบนี้ยืนยันด้วยการเขียนเทสต์ก่อนแก้ (RED) แล้วดูว่าอันไหนแดง
ผลคือ **แดงครบทั้ง 5 ปุ่ม**: `เรียก` · `เรียกคิวถัดไป` · `เสร็จ` · `ข้าม` · `เรียกซ้ำ`

ข้อเท็จจริงที่แผนยังไม่รู้ และรอบนี้วัดได้ — **`เรียกคิวถัดไป` กดซ้ำจะ "ดึงซ้อน" ไม่ใช่ "ข้ามผิด"**:

```
[ 'o1', { status: 'serving', servingAt: 1000, announcedAt: 1000 } ]
[ 'o1', { status: 'serving', servingAt: 2000, announcedAt: 2000 } ]
```

คลิกที่สองกลับไปดึง **o1 ตัวเดิม** ด้วยเวลาใหม่ ไม่ได้กระโดดไป o2 (เพราะ `waiting[0]` ยังเป็น o1
ใน closure เก่า) — B2 ปักทั้งสองอย่าง: เขียนครั้งเดียว **และ** o2 ต้องไม่โผล่ใน call list

## 2. ที่แก้ — `QueuePanel.tsx` เท่านั้น

`Set<string>` ใน `useRef` เก็บ id ที่เพิ่งส่ง status-transition ออกไปแต่ snapshot ยังไม่กลับมา

**ตัดสินใจ 3 เรื่อง ที่ควรอ่านก่อนแก้ต่อ:**

1. **กันเฉพาะ patch ที่มี `status`** — `ประกาศซ้ำ` ไม่เปลี่ยนสถานะ (spec เรียกมันว่า
   `serving (ไม่เปลี่ยนสถานะ)` ในตาราง action §3) การกดซ้ำๆ **คือตัวฟีเจอร์** ถ้ากันมันด้วย
   เกณฑ์ข้อ "ประกาศซ้ำ" ที่ติ๊กไปแล้วจะพังทันที — M3 พิสูจน์แล้ว (ดูตารางข้างล่าง)
2. **snapshot มา = ล้างทั้ง Set** ไม่ใช่ล้างเฉพาะ id ที่เห็นว่าเปลี่ยน — จงใจ
   ถ้าเขียนแล้ว snapshot ไม่กลับมา การล้างแบบแม่นยำจะทำให้ปุ่ม **ตายถาวร**
   ปุ่มตายกลางงานซุ้มแย่กว่าการเขียนเกินหนึ่งครั้งใน race ที่แพ้ไปแล้ว
3. **`ย้อนกลับ` ไม่ถูกกัน และปลดล็อกให้ด้วย** — undo ย้อน transition ตัวที่ถูกกันอยู่พอดี
   การกันมันคือทำให้ safety net ยิงไม่ออก M8 พิสูจน์ว่าถ้ากัน undo เทสต์ Undo เดิม **แดง 8 ตัว**

## 3. Mutation check — ทำนายก่อนรัน 8 ตัว ตรง 8 จาก 8

ทำนายชุดที่จะแดงไว้ก่อนรันทุกตัว แล้วเทียบ (เทสต์ในไฟล์นี้ตัวหนา, ไฟล์อื่นตัวธรรมดา)

| # | Mutation | ทำนาย | ผลจริง | ตรง? |
|---|---|---|---|---|
| M1 | ลบ `moved.current.clear()` ตอน snapshot มา | **D1** | **D1** + `skip…recall brings it back` | ✅ (ทำนายไว้กว้างๆ ว่า "อาจมีตัวอื่น") |
| M2 | ลบ `if (moved.current.has(order.id)) return` | **B1–B6, D1** (7) | **B1–B6, D1** (7) | ✅ ตรงเป๊ะ |
| M3 | ตัดเงื่อนไข `patch.status !== undefined` (กันทุก patch) | **C1, C2** + reannounce B2 | **C1, C2** + reannounce B2 | ✅ ตรงเป๊ะ |
| M4 | ลบ `moved.current.delete(undo.id)` ใน `runUndo` | **D3** | **D3** | ✅ ตรงเป๊ะ |
| M5 | ใช้ค่าคงที่ `'ANY'` แทน `order.id` (ล็อกรวม) | **B6, D3** | **B6, D3** | ✅ ตรงเป๊ะ |
| M6 | ลบ guard ของ `markDone` ใน `queueActions` | **A2** + ไฟล์อื่น | **A2** + `markDone only from serving` | ✅ |
| M7 | `markDone` ไม่ใส่ `doneAt` | **A1** + ไฟล์อื่น | **A1**, **B3**, **B6**, **D2**, **D3** + 3 ตัวไฟล์อื่น | ✅ |
| M8 | ให้ `runUndo` เคารพ guard ด้วย | **D2, D3** | **D2, D3** + Undo เดิม **8 ตัว** | ✅ |

### เทสต์ที่มี killer ตัวเดียว — ห้ามลบ

`A1` (M7) · `A2` (M6) · `B1` `B2` `B4` `B5` (M2) · `C1` `C2` (M3)

`C1`/`C2` สำคัญเป็นพิเศษ: มันคือตัวเดียวในไฟล์นี้ที่กันไม่ให้ใครไป "เก็บกวาด" เงื่อนไข
`patch.status !== undefined` ทิ้ง แล้วทำให้ `ประกาศซ้ำ` เงียบ

### 🚨 `E1` ไม่มี killer เลย — และนั่นคือความตั้งใจ

M1–M8 ฆ่า E1 ไม่ได้สักตัว **ไม่ใช่เพราะเทสต์อ่อน** แต่เพราะ E1 ไม่ได้พิสูจน์ว่าโค้ดถูก —
มันปักหมุด **ช่องว่างที่ยังเปิดอยู่** (ดูข้อ 4) killer ของมันคือ *การแก้ในอนาคต*:
วันไหนมีคนปิด cross-client race ได้จริง E1 จะแดง และนั่นคือสัญญาณให้มาอ่านไฟล์นี้ ไม่ใช่บั๊ก

## 4. ขอบเขตของหลักฐาน — อะไรที่ *ไม่* ได้พิสูจน์

- **เคสสองเครื่องยังไม่ถูกปิด** guard นี้เป็นของ panel instance ต่อ instance
  มันมองไม่เห็นการกดของอีกเครื่อง E1 เรนเดอร์ `QueuePanel` สองตัวแล้วกด `เรียก` ทั้งคู่ →
  **ได้ 2 writes** และเทสต์ยืนยันว่ายังได้ 2 อยู่ ไม่ได้แกล้งพิสูจน์ว่าแก้แล้ว
  ผลลัพธ์ปลายทางยัง *ถูก* (Firestore last-write-wins และทั้งสอง write ใส่ status เดียวกัน)
  แต่ "เขียนครั้งเดียว" **ไม่จริงข้ามเครื่อง** การปิดจริงต้องใช้ `runTransaction` หรือ
  conditional update ซึ่งแตะ repo layer + `firestore.rules` — อยู่นอกขอบเขตรอบนี้และ
  `firestore.rules` เป็น out-of-scope ของแผนด้วย
- **snapshot ที่มาโดยยังไม่มี write ของเราติดมา** จะปลดล็อกเร็วเกินไป การปลดล็อกผูกกับ
  "มี snapshot เข้ามา" ไม่ใช่ "write ของเรากลับมาแล้ว" — เลือกแบบนี้เพราะทางเลือกที่แม่นกว่า
  มี failure mode เป็นปุ่มค้างถาวร D1/D3 ปักไว้ว่าไม่มีอะไรล็อกค้างได้
- **ordersRepo และ display/chime ถูก mock ทั้งก้อน** ไม่มีอะไรถึง Firestore จริง
  "ไม่เขียนซ้ำ" = `updateOrderStatus` ไม่ถูกเรียกอีก **ไม่ได้** แปลว่า Firestore จะปฏิเสธ write ที่สอง
- **jsdom ไม่มี layout และไม่มี double-tap จริง** "กดสองครั้งโดยไม่มี snapshot คั่น" จำลองด้วย
  การคลิกสองทีโดยไม่เรียก `emit()` ซึ่งเป็น render generation เดียวกับที่ race จริงตกอยู่
- **ไม่ได้แตะ** `firestore.rules`, `firestore.indexes.json`, logic บัญชี/เมนู/comms,
  และไฟล์ใน `docs/superpowers/specs/`

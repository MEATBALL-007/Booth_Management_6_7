## 1. ข้อความจริงของเกณฑ์ (ไม่ใช่ที่แผนย่อไว้)

`docs/superpowers/specs/2026-08-03-ui-overhaul-design.md:50` (§4 Responsive rules):

> **จอใหญ่/TV (Display):** เลขคิวสเกลด้วย `clamp()` ให้ใหญ่ตามจอ
> (เช่น `clamp(96px, 22vw, 320px)`) **เห็นสุดห้อง**

สามคำที่ต้องแยกกันพิสูจน์ ไม่ใช่คำเดียว:

| คำในเกณฑ์ | แปลเป็นเงื่อนไขที่ตรวจได้ | เทสต์ |
|---|---|---|
| `clamp()` | มี `clamp(<px>, …, <px>)` จริง ไม่ใช่ขนาดคงที่ | B1 · C1 · C2 |
| **ตามจอ** | เทอมกลางต้องเป็นหน่วย viewport (`vw`…) — `px`/`rem` ไม่ผ่าน | A2 · B1 · C1 · C2 |
| **เห็นสุดห้อง** | เป็นข้ออ้าง**ลำดับชั้น**: เลขที่กำลังทำต้องใหญ่สุดบนผนัง | C3 · D2 |

⚠️ จุดที่ทำให้เกณฑ์นี้หลอกง่าย: **`clamp(96px, 220px, 320px)` เป็น CSS ที่ถูกต้อง

### ขอบเขตจริงของ clamp ที่ใช้อยู่ (ตัวเลขที่ควรรู้ ไม่ได้ปักไว้ในเทสต์)

`clamp(96px, 22vw, 320px)` → เทอม vw **ทำงานจริงเฉพาะช่วงจอกว้าง 436px – 1455px**
- แคบกว่า 436px → ค้างที่พื้น 96px
- กว้างกว่า 1455px → **ค้างที่เพดาน 320px** (จอ TV 4K ก็ได้ 320px เท่าจอ 1455px)

พูดให้ตรง: มันคือ "ใหญ่ตามจอ**ในช่วงหนึ่ง** แล้วหยุด" ไม่ใช่ "ใหญ่ตามจอไม่มีที่สิ้นสุด"
**ไม่ถือว่าผิดเกณฑ์** เพราะสเปกยกค่าชุดนี้มาเป็นตัวอย่างของตัวเองที่บรรทัด `:50`
เพดานคือสิ่งที่ `clamp` มีไว้ทำ — บันทึกไว้ตรงนี้เพื่อไม่ให้ใครอ่านเกณฑ์เกินจริง

หมายเหตุอีกชั้น: พื้น/เพดานเป็น **px** จึง**ไม่ถูกคูณ** ด้วย `html { font-size: 120% }`
ที่ `src/index.css:5` ต่างจากเม็ดเล็กที่เป็น utility หน่วย rem ซึ่งถูกคูณ 1.2

## 3. จุดที่ต้องตัดสิน: เกณฑ์ครอบเลขคิวตัวไหนบ้าง

`DisplayScreen` มีเลขคิว **สามขนาด** ต้องตัดสินว่าอันไหนอยู่ในเกณฑ์ ไม่ปล่อยเป็น "ไม่รู้"

**ตัดสิน: ครอบ (1) เลขที่กำลังทำ และ (2) เลขในการ์ดเตรียมตัว — ไม่ครอบ (3) เม็ดเล็ก**

บังคับด้วยตัวสเปกเอง ไม่ใช่รสนิยม:

1. **`:59` (§5.3 Per-screen application)** เขียนแยกบทบาทไว้ในบรรทัดเดียวกัน:
   *"NOW SERVING เลขใหญ่ glow + รายละเอียดเมนูใต้เลข, **UP NEXT pills สะอาด**"*
   → สเปกสั่งเองว่าเม็ดเล็กต้อง "สะอาด" (= เล็ก เรียบ) การเอา clamp ไปใส่คือ**ขัดคำสั่งข้อนี้**
2. **`:26` (§2 Glow rules)** ผูกการเน้นไว้กับ **"เลขคิวที่กำลังทำ"** เท่านั้น
3. **`:82` (§7 P3)** ตั้งชื่องานนี้ว่า *"Responsive polish + ตรวจทุก breakpoint + จอใหญ่ (Display clamp)"*
   และ commit ที่ทำงานนี้ชื่อ `89ed450 feat(ui): restyle Display screen + large-screen queue clamp`
   → เป้าคือ "เลขที่ต้องอ่านออกจากไกลบนจอใหญ่" ไม่ใช่ "ทุกตัวเลขบนหน้าจอ"
4. ในทางใช้งาน: ถ้าเม็ดเล็กสเกลตามจอด้วย **บันไดขนาดจะแบน** ซึ่งทำลายเกณฑ์ glanceable
   ของ spec `queue-pro-upgrade` (ข้อ "ขนาดบอกลำดับ") ที่ปิดไปแล้วรอบ 0020

**แต่ไม่ปล่อยเม็ดเล็กลอย** — สิ่งที่ล็อกแทนคือ *เหตุผล*ที่มันถูกยกเว้น:
เทสต์ **D2** บังคับว่าเม็ดเล็กต้อง**เตี้ยกว่าพื้น (min) ของการ์ดเตรียมตัว**
(28.8px < 56px ที่ root 120%) → วันที่มีคนทำให้เม็ดเล็กใหญ่ขึ้นมาแข่ง เทสต์แดงทันที
กฎนี้ยัง**รอดถ้าอนาคตมีคนให้เม็ดเล็กเป็น clamp เล็กๆ** (ซึ่งไม่ผิดอะไร) ต่างจากการปัก
"ห้ามมี clamp" เฉยๆ — ปักแบบนั้นจะกลายเป็นตัวขวางงานออกแบบในอนาคต

ส่วน **`size="card"`** (แผงคิว/Order Station) ล็อกด้วย **B2/B3** ว่า**ต้องไม่มี** clamp
— กันความผิดพลาดขาตรงข้าม: ใครก๊อป display scale ไปแปะการ์ดในคอลัมน์กว้างคงที่

## 7. ⚠️ ขอบเขตของหลักฐาน — อ่านก่อนเชื่อ

- **jsdom ไม่รัน cascade และไม่ layout เลย** ไม่มีเทสต์ตัวไหนในรอบนี้วัดพิกเซล วัด viewport
  หรืออ่าน computed font-size ทั้งหมดพิสูจน์ระดับ **token ที่ประกาศไว้ + โครงสร้าง DOM**
- แปลว่า **"เห็นสุดห้อง" ยังไม่ถูกพิสูจน์ระดับกายภาพ** สิ่งที่พิสูจน์คือ
  "ค่าที่เขียนไว้มีรูปแบบที่จะสเกลตามจอ และเรียงลำดับใหญ่-เล็กถูกต้อง"
  ปิดข้อนี้ระดับพิกเซลต้องเปิดเบราว์เซอร์จริงที่ 360/768/1024/1920 แล้ววัดขนาดจริง
  — **ไม่เคยทำ ไม่มีเทสต์ตัวไหนแกล้งทำเป็นทำแล้ว**
- E1/E2 อ่าน **ข้อความในซอร์ส** → class ที่ต่อสตริงตอน runtime มองไม่เห็น
- C1/C2/D2 ดีกว่าตรงที่อ่านจาก **DOM ที่ render จริง** จึงเห็นค่าที่ผ่าน props/primitive มาแล้ว

## 1. ขอบเขตของเกณฑ์ — ตัดสินแล้ว

สเปกกางข้ออ้างย่อยไว้ 3 ก้อนที่ §4.2:

| บรรทัด | ข้อความ |
|---|---|
| `:114` | Order Station: ปุ่มลัด 3 ปุ่ม (🆘 · 📦 · ✅) → `messages{kind:"alert", presetCode, scope:"all"}` |
| `:116` | **ทุกโหมด (Order/Display/HQ) รับ** → toast + **เสียงเบา** (ต่างจากเสียงเรียกคิว) + ปุ่ม ✔ ack |
| `:118` | **Display**: alert สำคัญขึ้น**แถบ**บนจอสั้นๆ ไม่รบกวนการโชว์คิว |

เกณฑ์ที่ต้องติ๊กพูดถึง **"toast"** และ **"ack ได้"** ซึ่งเป็นคำของบรรทัด `:116`
ส่วน `:118` ให้ Display ทรีตเมนต์ของตัวเอง (แถบ · สั้นๆ · **ไม่พูดถึง ack เลย**)

**→ ตัดสิน: เกณฑ์กิน HQ (Dashboard) + Order Station ของซุ้มอื่น ไม่กินแถบบน Display**

เหตุผลที่ชี้ขาดไม่ใช่การอ่านคำ แต่เป็น **ตัวโค้ดเอง**:
`visibleMessages()` (`src/comms/commsLogic.ts:14`) ตัดข้อความออกจากจอ **ก็ต่อเมื่อ `ackBy`
มี deviceId ของเครื่องนั้นแล้ว** — ไม่มีเงื่อนไขอื่นเลย ไม่มีเวลา ไม่มี auto-dismiss
จอลูกค้าไม่มีใครกด ✔ → **เอา `CommsToast` ไปแปะบน Display ตรงๆ = alert ค้างถาวรบนจอลูกค้า**
ปิดช่องนี้ให้ถูกต้องต้องเพิ่ม time window หรือ local dismiss เข้าไปใน `commsLogic.ts`
ซึ่ง **Out of scope ของรอบนี้เขียนว่า "ห้ามเปลี่ยน logic comms"**
→ ทำในรอบนี้ไม่ได้ **จึงล็อกเป็นเทสต์ `GAP:` พร้อมเหตุผล ไม่ปล่อยเป็นสถานะ "ไม่รู้"**

ข้อสังเกตประกอบ (ไม่ใช่ตัวชี้ขาด): 🆘 = "ขอคนช่วย" มีไว้เรียก **คน** จอที่ต้องเห็นคือจอที่พนักงานยืนอยู่
และ `:118` เขียนว่า "alert **สำคัญ**" = ตั้งใจให้ Display เห็นแค่บางส่วนที่กรองแล้ว ไม่ใช่ทุกใบ

**M12 ทำนายพลาดเรื่องขอบเขต** (ไม่ใช่เรื่องเป้าหมาย): jsdom **ไม่มี `AudioContext`**
→ คอนสตรัคเตอร์ throw ตอน render → ทุกเทสต์ที่ render จอพังตามไปหมด
เป็นข้อจำกัดของ jsdom ไม่ใช่ความไวของเทสต์ — ตัวที่ตั้งใจให้แดง (GAP-sound) แดงตามเป้า
บันทึกไว้เพราะรอบหลังที่จะ**สร้าง**เสียงจริงต้อง mock `AudioContext` ให้จอทุกจอ ไม่ใช่แค่ไฟล์เดียว

**สรุปการฆ่า**: เทสต์ทั้ง 15 ตัว **ถูกฆ่าอย่างน้อย 1 แบบ** ไม่มีตัวไหนรอดทุกแบบ
เทสต์ `GAP:` ทั้ง 3 ตัวถูกฆ่าด้วย mutation ที่จำลอง "มีคนมาปิดช่องว่าง" (M11) หรือ
"ตัวสแกนตาบอด" (M1/M4) → เป็น tripwire จริง ไม่ใช่ `expect([]).toEqual([])`

**revert ครบทุกครั้ง** — `git status --short` ว่างก่อน commit ทุกรอบ

## 5. ช่องว่างที่บันทึกไว้ (ตั้งใจไม่ปิดในรอบนี้)

**G1 — Display ไม่ได้รับ alert เลย** (§4.2 `:118`)
ปิดไม่ได้ในรอบนี้เพราะต้องแก้ `commsLogic.ts` (= logic comms, Out of scope)
ถ้าไม่แก้ logic แล้วแปะ toast ลงไป → alert ค้างถาวรบนจอลูกค้า **แย่กว่าไม่มี**
ตำแหน่งที่ควรไปคือ**ด้านบนจอ** (ตรงกับคำว่า "แถบบนจอ" ใน `:118`) เพราะมุมล่างถูกจองแล้วทั้งสองมุม:
ขวา = ปุ่มกลับหน้าตั้งค่า (`App.tsx:32`) · ซ้าย = donation thermometer (งานรอบ 0032 บน branch `_0032`)

**G2 — ไม่มีเสียงเบาสำหรับ alert** (§4.2 `:116` "เสียงเบา (ต่างจากเสียงเรียกคิว)")
มี `src/display/chime.ts` อยู่แล้วสำหรับเรียกคิว แต่ `CommsToast` ไม่เล่นเสียงอะไรเลย
เกณฑ์ที่ติ๊กไม่ได้พูดถึงเสียง → ไม่ทำให้เกณฑ์ตก แต่เป็นข้ออ้างของ §4.2 ที่ยังขาด

**G3 — ไม่มี time window** (§4.2 `:116` "ล่าสุด ~เวลาปัจจุบัน")
`visibleMessages()` ไม่รับพารามิเตอร์ `now` ด้วยซ้ำ → alert ของเมื่อวานที่ไม่มีใคร ack
ยังเด้งอยู่ในวันถัดไป **ผลจริงในงาน**: เครื่องที่เพิ่งเปิดจะเจอ alert เก่ากองรออยู่
(alert ใหม่ยังชนะเสมอเพราะเรียงใหม่→เก่า — เทสต์ C4 ล็อกไว้แล้ว จึงไม่กระทบเกณฑ์ข้อนี้)

**G4 — สองเครื่องพร้อมกัน / offline ยังไม่ถูกพิสูจน์**
`ackMessage` ใช้ `arrayUnion` ซึ่ง**ทนการ ack พร้อมกัน**ได้โดยธรรมชาติ (ต่างจากกรณี queue รอบ 0042)
แต่ไม่มีเทสต์ตัวไหนแตะ Firestore จริง → เป็นการอ่านโค้ด ไม่ใช่หลักฐาน

## 6. ขอบเขตของหลักฐาน (อ่านก่อนเชื่อ)

- jsdom **ไม่รัน cascade ไม่ layout** → toast ที่เป็น `fixed top-3` **ไม่ได้ถูกพิสูจน์ว่าไม่บังอะไร**
- **"ภายในไม่กี่วิ" พิสูจน์เชิงโครงสร้างเท่านั้น**: จอต่อ listener ไว้ และ toast โผล่จาก snapshot
  โดยไม่ต้องรีเฟรช/ไม่ต้องกดอะไร — **ไม่ได้จับเวลาจริงบนเน็ตจริง**
- **"เมื่อ online" ไม่ได้ทดสอบเลย** — `commsRepo` ถูก mock ทั้งโมดูล
  **ไม่เคยต่อ Firestore จริง ไม่เคยเปิดสองเครื่องจริง ไม่เคยลอง offline จริง**
- ปิดข้อนี้ระดับกายภาพต้องเปิดสองเบราว์เซอร์บน project จริงแล้วกดปุ่มดู — **ไม่เคยทำ**
